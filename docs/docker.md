# Docker Architecture & Deployment Guide — Step 4

This document outlines the containerization strategy for the **Cloud-Native Data Center Infrastructure Monitoring and Real-Time Analytics Platform**.

---

## 1. Why Docker is Used
Containerization ensures:
- **Environment Consistency**: Eliminates "works on my machine" issues by packaging Python dependencies and runtime binaries into reproducible artifacts.
- **Microservices Isolation**: Separates the telemetry generator service from the streaming broker.
- **Portability & Deployment**: Simplifies single-command deployment (`docker compose up -d`) on AWS EC2 or local development hosts.

---

## 2. What is Containerized
- **`telemetry-simulator`**: Single Python container encapsulating the realistic `DataCenterSimulator` engine and `KafkaTelemetryProducer`.
- **`kafka`**: Dedicated Apache Kafka broker container running in KRaft mode.

---

## 3. Why 20 Logical Servers are NOT 20 Containers
The 20 servers (`SRV001` through `SRV020`) represent **logical data center infrastructure topology** managed by the single simulation engine (`5 racks x 4 servers`). 

Creating 20 separate containers would introduce unnecessary CPU/memory overhead and container orchestration complexity. **The container is the deployment unit**, whereas logical servers are simulated data entities generated by the single container process.

---

## 4. Docker Network Architecture

Both services reside on a dedicated Docker bridge network (`monitoring-net`):

```
+-------------------------------------------------------------------------------+
| AWS EC2 Host                                                                  |
|                                                                               |
|   +-----------------------------------------------------------------------+   |
|   | Docker Network: monitoring-net                                        |   |
|   |                                                                       |   |
|   |  +-----------------------+           +-----------------------------+  |   |
|   |  | telemetry-simulator   |           | kafka                       |  |   |
|   |  | (Python App Container)|           | (Broker Container)          |  |   |
|   |  |                       |           |                             |  |   |
|   |  |  KafkaProducer        |===(9092)==> INTERNAL Listener           |  |   |
|   |  +-----------------------+           | (kafka:9092)                |  |   |
|   |                                      |                             |  |   |
|   |                                      | EXTERNAL Listener           |  |   |
|   |                                      | (0.0.0.0:9094)              |  |   |
|   +--------------------------------------|-----------------------------+  |   |
|                                          |                                    |
+------------------------------------------|------------------------------------+
                                           | (Port 9094)
                                           ▼
                              Databricks Structured Streaming
```

---

## 5. Kafka Internal Listener
- **Endpoint**: `kafka:9092`
- **Purpose**: Used for high-throughput container-to-container communication inside the `monitoring-net` bridge network. `telemetry-simulator` resolves hostname `kafka` to the Kafka container IP.

---

## 6. Kafka External Listener
- **Endpoint**: `<EC2_PUBLIC_IP_OR_DNS>:9094`
- **Purpose**: Used for external connections coming from Databricks clusters running outside the AWS EC2 container network.

---

## 7. Environment Variables & Configuration

The application reads configuration dynamically from environment variables, with sensible defaults:

| Variable Name | Docker Default | Local Default | Description |
| :--- | :--- | :--- | :--- |
| `KAFKA_BOOTSTRAP_SERVERS` | `kafka:9092` | `localhost:9092` | Kafka bootstrap broker endpoint |
| `KAFKA_TOPIC` | `server_telemetry` | `server_telemetry` | Target Kafka topic |
| `TELEMETRY_INTERVAL` | `5.0` | `5.0` | Emission interval in seconds |
| `NUM_RACKS` | `5` | `5` | Topology rack count |
| `SERVERS_PER_RACK` | `4` | `4` | Servers per rack (5x4=20 total) |
| `ENABLE_INCIDENTS` | `true` | `true` | Enables random incident injection |
| `SCENARIO` | `None` | `None` | Inject specific incident scenario |
| `KAFKA_CONNECT_RETRIES` | `15` | `10` | Reconnect attempt limit |
| `KAFKA_CONNECT_RETRY_INTERVAL` | `3.0` | `3.0` | Reconnect retry interval (seconds) |

## 8. Build & Management Commands

### Build Docker Images
```bash
docker compose build
```

### Start Containers in Background
```bash
docker compose up -d
```

### Check Container Status
```bash
docker compose ps
```

### View Telemetry Simulator Logs
```bash
docker compose logs -f telemetry-simulator
```

### Stop Containers & Clean Up Network
```bash
docker compose down
```

---

## 9. Verifying Kafka Telemetry

### List Topics
```bash
docker exec kafka /opt/kafka/bin/kafka-topics.sh \
  --list \
  --bootstrap-server localhost:9092
```

### Consume Telemetry Events
```bash
docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic server_telemetry \
  --from-beginning
```

---

## 10. Local Development vs. Docker vs. Databricks Endpoint Differences

- **Inside Docker**: `telemetry-simulator` connects to `kafka:9092`.
- **Outside Docker / Local Host CLI**: `kafka_producer.py` connects to `localhost:9092`.
- **External Databricks Cluster**: Databricks connects to `<EC2_PUBLIC_IP>:9094`.
