# Step 5: Kubernetes Orchestration & Server Sharding Guide

This directory contains the Kubernetes manifests and documentation for deploying the **Cloud-Native Data Center Infrastructure Monitoring Telemetry Simulator** on a Kubernetes cluster (k8s / K3s / Minikube / EKS).

---

## 1. Why Kubernetes is Used
While Docker Compose manages containers on a single host, Kubernetes provides cloud-native orchestration capabilities:
- **High Availability & Self-Healing**: Automatically detects crashed or deleted pods and schedules immediate replacements.
- **Horizontal Pod Autoscaling**: Dynamically scales simulation pods up or down based on load.
- **Declarative Configuration**: Manages infrastructure states using declarative YAML manifests.
- **Service Discovery & Config Management**: Decouples application configuration via `ConfigMap` and internal DNS.

---

## 2. Critical Architectural Principle: 20 Logical Servers vs. Kubernetes Pods

> **IMPORTANT**: 20 logical servers (`SRV001` through `SRV020`) DO NOT EQUAL 20 Kubernetes Pods.

The 20 servers represent **simulated data center hardware topology** generated by the Python simulation engine. The Kubernetes Pod is the **application process deployment unit**. 

When scaling the Kubernetes Deployment to multiple replicas (e.g., 2 pods), the application uses **deterministic server sharding** to partition the 20 logical servers among active pods.

---

## 3. Server Sharding & Duplicate Prevention Math

To prevent multiple pod replicas from emitting duplicate telemetry for the same logical server, the simulator uses a round-robin partitioning algorithm:

$$\text{count} = \lfloor \frac{\text{total\_servers}}{\text{total\_shards}} \rfloor + (1 \text{ if } \text{shard\_index} < \text{remainder} \text{ else } 0)$$

### Shard Allocation Examples

#### Single Replica Mode (`replicas = 1`)
- **Pod 0** (`shard_index = 0`): `SRV001` – `SRV020` (all 20 servers).

#### Two Replicas Mode (`replicas = 2`)
- **Pod 0** (`shard_index = 0`): `SRV001` – `SRV010` (10 servers).
- **Pod 1** (`shard_index = 1`): `SRV011` – `SRV020` (10 servers).
- **Union**: `SRV001`..`SRV020` (20 unique servers).
- **Intersection**: $\emptyset$ (0 duplicate servers).

#### Four Replicas Mode (`replicas = 4`)
- **Pod 0**: `SRV001` – `SRV005` (5 servers)
- **Pod 1**: `SRV006` – `SRV010` (5 servers)
- **Pod 2**: `SRV011` – `SRV015` (5 servers)
- **Pod 3**: `SRV016` – `SRV020` (5 servers)

#### Telemetry Emission Rate Invariance
With 20 servers emitted every 5 seconds, the total aggregate telemetry rate remains **~4 events/second** regardless of whether 1, 2, or 4 replicas are running.

## 5. Resource Requests & Limits Rationale

Defined in [`deployment.yaml`](file:///d:/Data%20Center/kubernetes/deployment.yaml):
```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 250m
    memory: 256Mi
```
- **CPU Request (100m)**: Guarantees 0.1 CPU cores for smooth temporal continuity calculations.
- **Memory Limit (256Mi)**: Provides ample headroom for Python runtime while protecting node memory on small EC2 instances.

## 6. How to Deploy & Verify

### 1. Apply Namespace & Configuration
```bash
kubectl apply -f kubernetes/namespace.yaml
kubectl apply -f kubernetes/configmap.yaml
```

### 2. Deploy Telemetry Simulator
```bash
kubectl apply -f kubernetes/deployment.yaml
kubectl apply -f kubernetes/service.yaml
```

### 3. Verify Single-Replica Deployment Status
```bash
kubectl get pods -n data-center-monitoring
kubectl get deployments -n data-center-monitoring
```

### 4. Inspect Pod Logs
```bash
kubectl logs -n data-center-monitoring -l app=telemetry-simulator
```
*Expected Output:* `Assigned Shard: SRV001..SRV020 (20 servers assigned)`

---

## 7. Scaling & Self-Healing Verification

### Scaling to 2 Replicas
```bash
kubectl scale deployment telemetry-simulator --replicas=2 -n data-center-monitoring
```

Verify two pods running:
```bash
kubectl get pods -n data-center-monitoring
```

Check pod logs for shard division:
- Pod 0 log: `Assigned Shard: SRV001..SRV010`
- Pod 1 log: `Assigned Shard: SRV011..SRV020`

### Pod Self-Healing Test
Delete one active pod to verify automatic replacement:
```bash
kubectl delete pod <pod-name> -n data-center-monitoring
```
Kubernetes immediately provisions a replacement pod, which automatically resumes its assigned server shard without duplicating server ownership.
